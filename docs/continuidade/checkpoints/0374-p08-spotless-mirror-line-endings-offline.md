## Causa demonstrada

O espelho 0373 `C:\Users\lucas\p08m0373` não tem `.git`. Uma cópia nova `C:\Users\lucas\p08-spotless-0374`, fora do checkout, conservou **2170/2170 SHA** do inventário candidato 0367 (`mirror-copy-proof.json`, SHA `CD0A7643173EF54422D2C969C30216EC24341A2D3CD9E36E2208443CF60FC3E5`). Três amostras, incluindo a IT corrigida, tinham **zero CRLF** e LF 72/887/127; seus SHA foram idênticos no worktree, espelho e cópia. A IT conservou `3C6462058679A04B486927F26B82D8D1F70D78FB0411A503218F7658AEBCA2B0`.

O descritor local do Spotless Maven 3.10.0 define `lineEndings=GIT_ATTRIBUTES_FAST_ALLSAME` por padrão. No checkout, `git check-attr eol` retorna `lf` para as amostras, conforme `* text=auto eol=lf` e `.editorconfig`. Fora de um repositório Git, a lógica local `GitAttributesLineEndings` não dispõe de worktree/config do repositório e usa o ending padrão derivado da plataforma/config; em Windows ele divergiu dos bytes LF. Prova diferencial no **mesmo** snapshot sem Git: `spotless:check` padrão saiu 1, **1210/1210 Java** precisavam de mudança (`spotless-default-repro-2.log`, SHA `7461CA6C6DC58720454F1249E317CBA3ECCAD085412C3C3F94635BDA549EED99`). Após acrescentar só `<lineEndings>UNIX</lineEndings>` no POM da cópia, o mesmo goal saiu 0, **0/1210** precisavam de mudança (`spotless-unix-repro.log`, SHA `1265E0FE981ECBCCA169F04221EAA9F40F0E20930EA9E117911C486CC4CECEE3`). Nenhum Java foi reformatado. A inferência causal é a resolução diferente dos finais de linha pelo default dependente de Git; a troca controlada de um parâmetro elimina o FAIL.

O wrapper Runtime de 0367 rodava `spotless:apply` antes do lifecycle `test-compile` em cópia **dentro** do checkout Git, onde o atributo `eol=lf` era visível; depois o check reportava PASS. O inventário A/B 0367 já demonstrava igualdade dos fontes Java antes/depois, portanto não há prova de que `spotless:apply` tenha modificado os 1210 naquele build. Ainda assim, o `apply` podia mascarar uma falha futura e o bloco posterior podia copiar Java formatado ao worktree; essa rota foi removida. Duas primeiras invocações da reprodução não chegaram ao Maven válido (o snapshot de pacote não continha `mvnw.cmd`; depois PowerShell tratou a mensagem nativa de `JAVA_TOOL_OPTIONS` como erro antes de registrar log). A execução controlada seguinte usou Maven 3.9.14 do cache, sempre `--offline`, sem URL/profile/JDBC; os fracassos de invocação não foram convertidos em PASS.
